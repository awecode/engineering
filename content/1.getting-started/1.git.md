## Commit Messages

- Adhere to conventional commit messages.
- Not everything is a chore. Use appropriate commit types.
- Make use of prefixes like `perf:` and `refactor:` as well.
- Keep commits atomic and focused on a single change.
- Write clear and concise commit messages.

## Branching Strategy

- Maintain three fixed branches:
  - `main`: Represents the production-ready state
  - `staging`: Represents the pre-production state for final testing
  - `develop`: Main branch for development work

- Branch hierarchy: `main` < `staging` < `develop`

- For new features and bug fixes:
  - Create feature branches from `develop` using the format: `feat/<feature-name>`
  - Create bug fix branches from `develop` using the format: `fix/<bug-description>`

## Merging and Rebasing

- When moving changes up the hierarchy (`develop` -> `staging` -> `main`):
  - Use merge commits
  - Example: `git checkout staging && git merge develop`

- When updating lower branches with changes from higher branches:
  - Use rebase
  - Example: `git checkout develop && git rebase staging`

- Keep `develop` up-to-date with `staging`, and `staging` up-to-date with `main` regularly.

- When merging feature or fix branches into `develop`, use squash and merge to keep history clean.

## General Practices

- Regularly pull from the `develop` branch to stay up-to-date when working on feature or fix branches.
- Never commit directly to `main` or `staging`. All changes should go through `develop` first.
- Use pull requests for code reviews before merging into `develop`.
